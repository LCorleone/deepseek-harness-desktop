  • 项目构成：开源 DSH Desktop（社区版 v2.0.2）＋ 公司安全护栏层（72 个安全 commit，分 P1–P4 四阶段）。 核心目标：锁定部署，用户只能安装公司审签过的插件。

  • 没有私有分叉：桌面产品本身也以标准插件形式接入运行时（「万物皆插件」）， 我们没有 fork 出一套私有代码。

锁定部署：桌面端出厂即固定为公司审定的配置，用户无法自行切换插件来源。
submodule（子模块）：以固定版本「钉」在本仓库内的上游代码只读副本，仅供审计对照。
fail-closed（默认拒绝）：任何配置缺失或校验失败，一律按「不安全」处理，宁可不用也不放行。
ed25519：一种高效数字签名算法——公司用私钥「盖章」，客户端用公钥验章，内容被篡改即刻被发现。
Cordis 容器：DSH 的插件运行容器，负责装载、隔离并连接各个插件。
yarn patch：对 npm 已发布包打补丁的官方机制，不需要改动上游源码仓库。
integrity（完整性指纹）：npm 官方为每个包版本计算的防篡改校验值。
app.asar：Electron 应用的资源打包档案（可整体校验完整性的「封装盒」）。
loopback（127.0.0.1 回环）：仅本机进程可访问的网络通道，外部机器无法连入。
序列号棘轮：只增不减的计数器，旧目录无法冒充新目录（防回滚、防重放）。
Electron fuses（保险丝）：Electron 官方提供的开关，可永久关闭危险能力（如以 Node 模式运行程序）。
2026-09-01 更新 权威模式（signed-tree）已在试点 fleet 实机激活；发布链路已全自动化，上线零人工操作；SSO 启动门禁落地。 攻击视角下用户尝试各种绕过手段的实测问答，见第 4 章。

01产品与仓库结构本项目由什么构成

本章结论：仓库 = 一个根工作区 + 四个职责清晰的组成部分；上游源码只读钉定、零修改， 我们发布的运行时 100% 来自 npm 官方包。公司价值全部沉淀在护栏层，不产生维护分叉的长期负担。

根仓库（Yarn workspace）＝ 公司 fork：社区版 v2.0.2 之后新增 72 个安全 commit（origin 指向社区上游 anywhere-labs）
deepseek-harness/
只读 · 零修改
上游源码，pinned git submodule（固定在 b150a55 / v0.1.1-rc.2）。 只作审计对照、不参与构建；verify-layout.mjs 强制校验其「干净且与 pin 一致」。
dsh-plugin-desktop/
公司主力 · 已实装
Electron 桌面壳。它本身就是一个标准 DSH 插件，与第三方插件走同一套接入机制（详见第 2 章）。
dsh-community-market/
已实装 · 已锁定
插件市场。已实装并内置于产品，锁定为公司签名目录——市场上能看到的插件全部经公司审签。
dsh-community-fabric/
纯文档
社区插件契约 RFC（第三方插件如何合规接入的规范草案），当前不含可执行代码。

关键事实

  • 发布产物中的 DSH 运行时 100% 来自 npm 官方包 @deepseek-ai/*@0.1.1-rc.2， 其中 11 个包经 yarn patch（对官方发布包打补丁，不动上游源码）修补。
  • submodule 仅为审计参照：构建产物不来自它，校验脚本却时刻盯着它——一旦有人改动上游目录，构建即失败。
  • git 拓扑：origin = 社区上游 anywhere-labs；fork = 公司版。公司在 v2.0.2 之后新增 72 个安全 commit，全部位于护栏层。
为什么坚持「上游零修改」？ 改上游源码 = 制造私有分叉 = 社区每次升级都要人工合并，长期成本最高。护栏放外围层（策略、签名、验签、打包）， 上游升级时护栏代码无需合并冲突处理，跟随成本最低。

02运行架构「桌面即插件」—— 没有分叉，只有组合

本章结论：桌面壳不是「魔改版 DSH」，而是以标准插件身份接入官方运行时容器； 界面运行在强沙箱的渲染进程里，只通过本机回环通道取数据。这是字面上的架构事实，不是宣传口号。

启动链（自上而下依次装载）

  1. Electron 主进程启动，单实例锁生效（防止多开导致的会话分裂）。
  2. 调用上游官方 boot()（不是我们的定制入口），建立 Cordis 容器 root。
  3. Loader 依次挂载：官方 dsh-base + dsh-web-app。
  4. 挂载桌面插件 7 个模块：desktop-shell（窗口/托盘）、terminal（终端）、updates（更新）、diagnostics（诊断）、notifications（通知）、pnpm（包管理）、profiles（配置档案）。
  5. 挂载锁定版 community-market（公司签名目录）。
  6. 挂载白名单第三方插件（仅签名目录内条目）。以上全部组成同一个 Cordis 运行时。

「桌面即插件」的实现依据

  • dsh-plugin-desktop 的 package.json 声明了标准 DSH 插件字段： dsh.client.inject 与 dsh.bundle.patch: cordis.patch.yml—— 与第三方插件走同一套组合机制。
  • 对第三方插件仅公开 2 个服务契约：dsh-plugin-desktop/profile-service 与 dsh-plugin-desktop/pnpm。 攻击面小、边界清晰。

渲染层安全（用户界面的隔离）

  • BrowserWindow 强制 sandbox + contextIsolation，禁用 nodeIntegration（页面代码碰不到 Node 系统能力，彼此隔离）。
  • 页面只加载 127.0.0.1 loopback 上的官方 Web UI（外部网络根本连不进这条通道）。
  • preload 脚本仅暴露 1 个文件路径 API；没有 renderer IPC 插件面（界面层没有可供插件利用的通信后门）。

03安全架构 · 五层防线核心章节

本章结论：安全设计遵循「纵深防御」——不依赖任何单点，五层各自独立承重： 即使某一层被突破，下一层仍能拦截。安装时拦一次（L1–L3），启动时再拦一次（L4），产品自身供应链再加固一次（L5）。 所有防线的默认行为都是 fail-closed（默认拒绝）。

L1嵌入式部署策略阶段 P1

拦什么：产品出厂后被改成「非锁定」配置的可能。怎么拦：把策略焊死在应用包内部。

  • 策略为 6 字段冻结 schema：locked（锁定开关）、公司目录源、manifest URL、禁 home patch、禁手动装插件、ed25519 信任根。
  • 构建时将策略资产嵌入 app.asar 内；默认出货 release（锁定）变体——即使构建时忘记配置，出厂的也是锁定版（fail-closed）。
  • 运行时优先读取 asar 虚拟归档内的策略副本，封死「改本地明文 JSON 文件」这条最廉价的篡改通道。

L3签名插件目录阶段 P2

拦什么：目录本身被伪造或篡改。怎么拦：整条目录由公司私钥签名，客户端只认签名。

L4启动验签承重墙阶段 P2 · 最终兜底

拦什么：一切绕过安装环节的「既成事实」——包括外部工具直接写盘的插件。怎么拦：每次启动重新验一遍，装了也白装。

  • 时机最早：每次启动、解析任何不可信配置之前执行，不给恶意代码任何先跑起来的机会。
  • 逐项校验：对每个第三方插件依次验证——签名 → 精确条目 → lockfile 一致 → 安装回执树摘要。
  • 不通过即拒载：剔除该插件，但应用本身正常启动（单个坏插件不能瘫痪整个产品）。
  • 免疫名单：官方插件、桌面插件、市场核心插件在免疫名单中永不过滤（它们由官方渠道与 L5 保障，避免误伤基本功能）。
为什么叫「承重墙」 这是最后一道独立承重的防线：哪怕 L2 的某个入口将来出现疏漏，只要插件未经公司签名，启动时就进不了运行时—— 「装得进、跑不起来」。
L5供应链与发布加固阶段 P3 / P4

拦什么：对产品自身的攻击（篡改程序、劫持更新、伪装运行时）。怎么拦：发布物全链路签名与门禁。

  • Electron fuses：禁 runAsNode（防把桌面程序当 Node 脚本引擎滥用）、启用 ASAR integrity（应用资源被改即拒绝运行）。
  • 更新强制验签：更新包必须携带 detached ed25519 签名，验签失败绝不落盘。
  • 独立 Node 运行时：捆绑自带、校验过的 Node 运行时，不依赖用户机器上来源不明的 Node。
  • 启动自检报告：启动时生成安全自检结果，供诊断导出与审计。
  • 发布前 preflight 门禁：缺信任根、目录未验签——直接构建失败，不合格产物出不了门。

04攻击视角下的插件防护问答用户尝试不同手段时，系统如何响应（全部经过实机验证）

本章结论：换一个攻击视角——用户想用各种手段绕过「锁定部署」时，系统如何响应。 以下 8 个问题与响应均经过实机验证，结论对应「拒绝 / 不生效」。

Q1我从市场以外的渠道（npm 网站、同事传文件）拿到插件，手动装进去行不行？

不行。插件加载的唯一入口是启动验签：不在公司签名目录（ed25519 签名的 manifest）里的插件，应用启动时直接拒载（allowManualPluginAdd=false 的服务级语义）。装进磁盘也永远不生效。

Q2我修改已经安装的插件文件，植入自己的代码呢？

不行。权威模式（signed-tree）每次启动对插件文件树做实测，与公司签名摘要比对，不一致即拒载。安装凭据（receipt）在权威模式下无决策权——删除或伪造它都没有意义。（该模式已在试点 fleet 实机激活，sequence 7 起。）

Q3我改本地配置文件，把插件源指向我自己的服务器？

不行。插件目录源与签名信任根在构建时嵌入应用内部（只读），配置文件里没有任何安全字段。改配置最坏的结果是把应用改坏（自己启动异常），永远改不动信任边界。

Q4我在内网伪造/重放一个目录清单（假服务器、hosts 劫持、中间人）？

不行。目录清单必须通过 ed25519 验签——没有公司私钥就签不出合法清单；序列棘轮拒绝一切回退（低序列硬拒、同序列异内容拒绝/自愈）。看到清单内容本身毫无帮助：签名值和摘要本来就是公开物（如同 TLS 证书），读权限不构成任何攻击面。

Q5我绕过界面，直接调用程序内部接口强行开启插件？

写路径在服务层被管制（危险权限档已从服务端配置表删除，不提供手动插件添加接口）。理论残余：直接向本机回环端口裸注入事件、或手工运行安装目录内的 CLI 工具——两者都已登记为「推广前复审」事项，其前提是用户刻意进行技术性绕过，等同于用户本来就拥有系统终端的场景，不属于普通用户可达路径。

Q6我找一个旧版本的安装包（没有这些防护的老构建）用？

首次启用权威模式时有 fleet 门禁（要求全部客户端已升级到支持签名目录的构建）；安装包只通过受控渠道分发。已知边界：栅栏强度取决于最旧可运行版本，旧安装包管理已列入推广前检查项。

Q7我让 AI 助手（应用内的 agent）帮我装插件、改配置？
  • ① 指导层：系统提示词注入公司安全条款，拒绝协助安装插件 / 修改桌面端配置。
  • ② 权限层：危险权限档（full access）已从产品中移除，agent 的文件操作受沙箱与审批约束。
  • ③ 硬栅栏：真正的硬栅栏是上面的签名链——即使提示词被诱导绕过，agent 也没有任何途径让未签名插件通过启动验签。
Q8内网同事都能看到这个目录清单，会不会有风险？

清单内容（包名、版本、文件树摘要、签名值）不含任何秘密——客户端本来就是匿名拉取的，这是签名体系的正确形态。真正需要保护的是签名私钥与发布凭据，它们分别保存在 CI 密钥库与受控仓库，不随应用分发。

05关键问题澄清管理层最可能问的两个问题

Q1我们是否修改了上游？以后升级能不能跟上？
  • 源码层：零修改。submodule 被强制校验「干净 + pin 一致」（verify-layout.mjs），任何对上游目录的改动都会被构建拦下。
  • 运行时层：11 个官方 npm 包经 yarn patch 修补。其中 9 个是社区版自带（UI 修补）， 公司自有的仅 2 个行为级修复：dsh-agent-loop（空名工具调用防护）、dsh-token-meter（计量缓存修复）。
  • 跟进能力：有文档化的升级流程（pin 更新独立提交、upstream.json 三重校验）。
  • 成本点（需要管理层知悉）：patch 打在编译产物上，上游大版本升级时 11 个 patch 需要重放； 且上游社区版已领先我方基线 184 commits，需要安排升级窗口（见第 6 章建议 ③）。
Q2桌面产品本身是不是 DSH 插件？这样做到底图什么？
  • 是。桌面壳以标准插件声明（dsh.client.inject ＋ dsh.bundle.patch: cordis.patch.yml） 接入官方运行时容器，与第三方插件使用同一套组合机制——「桌面即插件」是字面的架构事实。
  • 收益一（安全）：护栏通过官方组合机制施加，不被绕过的同时不制造私有分叉。
  • 收益二（兼容）：市场锁定也是通过组合层剥离不可信 provider 行实现的，无需改动上游一行代码， 与上游生态保持兼容。
